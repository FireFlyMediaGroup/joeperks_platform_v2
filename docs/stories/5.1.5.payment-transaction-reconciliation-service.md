## Story Context

- Integrates with: Stripe Connect Integration (Story 5.1) and Payment Processing Service
- Technology: Medusa.js backend, TypeScript, PostgreSQL with MikroORM

- Touch points: Payment transactions, Stripe webhooks, financial reporting system

## User Story

As a **platform financial administrator**,
I want **automated daily reconciliation of payment transactions with Stripe settlements**,
So that **I can ensure financial accuracy and quickly identify any discrepancies in revenue processing**.

## Acceptance Criteria

**Functional Requirements:**
1. Daily automated reconciliation matches platform transactions with Stripe settlement data
2. Discrepancy detection flags mismatched amounts, missing transactions, or duplicate entries
3. Reconciliation reports are generated with detailed transaction matching results

**Integration Requirements:**
4. Existing payment processing continues to work unchanged
5. New reconciliation follows existing service pattern from payment.service.ts
6. Integration with Stripe Connect webhooks maintains current behavior

**Quality Requirements:**
7. Reconciliation logic is covered by comprehensive unit and integration tests
8. Reconciliation process handles edge cases (refunds, disputes, partial settlements)
9. No regression in existing payment functionality verified

## Technical Notes

- **Integration Approach:** Extends existing PaymentService with reconciliation methods
- **Existing Pattern Reference:** Follow service pattern from apps/api/src/services/payment.service.ts
- **Key Constraints:** Must handle complex revenue splitting and multi-party settlements

## Reconciliation Process Flow

**Daily Reconciliation Steps:**
1. **Data Collection**: Retrieve platform transactions and Stripe settlement data
2. **Transaction Matching**: Match platform records with Stripe payment intents
3. **Amount Verification**: Verify revenue splits match expected calculations
4. **Discrepancy Detection**: Identify mismatched, missing, or duplicate transactions
5. **Report Generation**: Create detailed reconciliation reports with findings

**Reconciliation Scenarios:**
- Standard payments with revenue splitting
- Refunded transactions and adjustments
- Disputed charges and chargebacks
- Failed payments and retries
- Partial settlements and holds

## Dev Notes

### Previous Story Integration
**From Story 5.1**: Stripe Connect Integration provides payment processing and webhook infrastructure.
**From Payment Service**: Existing payment.service.ts provides transaction data access patterns.

### Data Model Extensions
**Reconciliation Entity**:
- Primary key: reconciliation_id (UUID)
- Date fields: reconciliation_date, settlement_date, created_at
- Status fields: status (pending, completed, failed), discrepancy_count
- Summary fields: total_transactions, matched_count, amount_matched
- Results: discrepancies (JSONB), reconciliation_summary (JSONB)

### Reconciliation Types
**Discrepancy Categories:**
- AMOUNT_MISMATCH: Revenue split doesn't match Stripe transfer
- MISSING_PLATFORM: Transaction exists in Stripe but not in platform
- MISSING_STRIPE: Transaction exists in platform but not in Stripe settlement
- DUPLICATE_TRANSACTION: Same transaction processed multiple times
- TIMING_DIFFERENCE: Transaction processed but settlement pending

### Stripe Integration Points
**Settlement Data Sources:**
- Stripe Balance Transactions API for settlement details
- Stripe Transfers API for Connect account payouts
- Stripe Payment Intents API for transaction details
- Stripe Webhook events for real-time reconciliation triggers

### Reconciliation Logic
**Matching Algorithms:**
- Exact match by Stripe payment intent ID
- Fuzzy matching by amount, date, and customer details
- Multi-party transaction reconstruction from Stripe transfers
- Time window matching for processing delays

### Reporting Integration
**Report Types:**
- Daily reconciliation summary (high-level metrics)
- Detailed discrepancy reports (transaction-level issues)
- Monthly financial reconciliation (accounting integration)
- Real-time reconciliation dashboard (finance team monitoring)

## Risk Assessment

**Primary Risk:** Reconciliation process missing complex multi-party transaction scenarios
**Mitigation:** Comprehensive test scenarios covering all revenue split combinations and edge cases
**Rollback:** Feature flag to disable automated reconciliation if accuracy issues arise

- [ ] Reconciliation adds minimal load to payment system
- [ ] Database schema changes are additive only
- [ ] Performance impact on payment operations is negligible
