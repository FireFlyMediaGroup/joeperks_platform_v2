# Story 1.3: User Management Service Implementation

## Status
Draft

## Story
**As a** platform developer,
**I want** to implement the user management service with Kinde synchronization,
**so that** the platform can manage user profiles, roles, and organization memberships across all user types.

## Acceptance Criteria
1. User CRUD operations are implemented with Kinde user ID mapping
2. User profile synchronization with Kinde is functional
3. Organization membership management supports RBAC roles
4. User type-specific operations are implemented for all user types
5. User status management (active, suspended, inactive) is functional
6. User search and filtering capabilities are available
7. Webhook integration maintains user data consistency with Kinde
8. User session management integrates with authentication service

## Dev Notes

### Previous Story Insights
**From Story 1.1**: Authentication service provides JWT tokens with user context and organization information.  
**From Story 1.2**: Database schema includes users, organizations, and organization_members tables with Kinde integration fields.

### Data Models Integration
**User Entity Operations** [Source: architecture/database-schema.md#users]:
- Primary key: `id` (UUID)
- Kinde mapping: `kinde_user_id` (unique identifier)
- User types: platform_admin, roaster, organization, customer
- Status management: active, suspended, inactive
- Profile fields: email, given_name, family_name, last_login

**Organization Member Operations** [Source: architecture/database-schema.md#organization_members]:
- Role management: admin, campaign_manager, viewer
- Kinde membership sync: `kinde_membership_id`
- Permission caching: `permissions` JSONB field
- Status tracking: invited_at, joined_at timestamps

### API Integration Points
**User Management Endpoints** [Source: architecture/api-specification.md#auth]:
- User context from `/auth/validate` endpoint
- Organization invitation via `/auth/organizations/{id}/invite`
- User profile data in AuthenticatedUser schema
- Organization context in authentication responses

### Component Specifications
**User Management Requirements** [Source: architecture/components.md#authentication-service]:
- **Member Management**: Streamlined invitation and role assignment workflows
- **Session Management**: Secure JWT tokens with organization context and feature flag claims
- **Multi-tenant Organizations**: Each fundraising organization maps to a Kinde organization
- **Role-Based Access Control**: Admin, campaign_manager, viewer roles with granular permissions

### File Locations
**Service Files** [Source: architecture/source-tree.md#services]:
- `apps/api/src/services/user.service.ts` - Core user management service
- `apps/api/src/services/organization-member.service.ts` - Membership management
- `apps/api/src/services/auth.service.ts` - Integration with authentication

**API Routes** [Source: architecture/source-tree.md#api]:
- `apps/api/src/api/users/` - User management endpoints
- `apps/api/src/api/auth/webhooks.ts` - Kinde webhook handlers for user sync

**Shared Libraries** [Source: architecture/source-tree.md#libs]:
- `libs/auth-utils/src/rbac-helpers.ts` - Role and permission utilities
- `libs/shared-types/src/auth/user.types.ts` - User and role type definitions

### Technical Constraints
**RBAC Requirements** [Source: architecture/security-considerations.md#rbac]:
- **Platform Admin**: Full system access across all organizations and roasters
- **Organization Admin**: Full access within their organization, can invite members
- **Campaign Manager**: Can create/edit campaigns, view analytics within organization
- **Organization Viewer**: Read-only access to organization data and campaigns
- **Roaster Admin**: Full access to roaster portal, partnership approvals
- **Roaster Staff**: Order fulfillment and inventory management
- **Customer**: Purchase access, order history, profile management

**Security Patterns** [Source: architecture/security-considerations.md#authentication]:
- Organization context MUST be extracted from token claims
- Role-based access control MUST be enforced at service level
- User data synchronization MUST maintain consistency with Kinde
- Permission caching MUST be updated when roles change

### Integration Dependencies
**Authentication Service Integration**:
- Requires Story 1.1 (Authentication Service) for JWT token validation
- Uses auth middleware for user context extraction
- Integrates with feature flag service for user-specific flags

**Database Integration**:
- Requires Story 1.2 (Database Schema) for user and membership tables
- Uses TypeORM entities for data operations
- Implements proper foreign key relationships
